Внутренний инструмент массового импорта контента в WordPress.

== Description ==

Site Builder — это плагин для автоматического развертывания WordPress-сайтов из подготовленных архивов контента.

**Основные возможности:**

* **FSR Import** — основной режим импорта: файловая структура архива (папки с `index.md`/`index.html` и флагами в именах) превращается в иерархию страниц WordPress. Поддерживает два режима:
  * **Создание сайта** — полный импорт с нуля, включая главную, меню, лого, иконку, стили
  * **Добавление страниц** — расширение уже работающего сайта без затрагивания существующего контента
* **Расписание `[DLY]`** — отложенная публикация: всё сразу, по странице в день, либо растянуть на N дней
* **Конструктор темы** — генерация собственной WordPress-темы из выбранных вариантов шапки (3), подвала (3) и цветовой схемы (3). Тема создаётся в `wp-content/themes/site-builder-generated/` и сразу активируется. Drop-in архитектура: добавление новых вариантов — просто новые файлы в папке `templates/theme/`
* **Автопривязка меню** к локациям активной темы через стандартный `theme_mod`
* **Откат** — любой импорт можно полностью откатить: страницы, меню, картинки в медиатеке, theme_mod'ы возвращаются в предыдущее состояние

== Installation ==

1. В админке WordPress откройте «Плагины → Добавить новый → Загрузить плагин».
2. Выберите ZIP-файл плагина и нажмите «Установить сейчас».
3. После установки нажмите «Активировать».
4. В сайдбаре админки появится пункт меню «Site Builder».

= 1.1.4-beta4 =
**Полная переработка SEO-цепочки чтения и записи мета-полей.** Пофикшена критическая проблема: разработчики не могли отредактировать SEO поля через админку, потому что импорт писал данные в один набор ключей (Yoast/RankMath), а тема читала совсем другой (`_custom_seo_*`, которых никто не создавал). В итоге правка Yoast-ключей ни на что не влияла, а поле `description` из frontmatter вообще терялось на пути до тега `<meta description>` если Yoast не установлен.

* **Фикс 1: гарантированные fallback-ключи в fsr_\* при импорте.** Плагин теперь всегда сохраняет `title` и `description` из frontmatter в отдельные ключи `fsr_title` и `fsr_description` — независимо от настроек Field_Mapping. Значит frontmatter-данные всегда доступны для чтения темой, даже если Yoast/RankMath не установлены или маппинг был переконфигурирован. Ключи без префикса `_` — видны в стандартной Custom Fields панели.
* **Фикс 2: тема читает все ключи которые пишет импорт.** Модуль `inc/seo.php` расширен полной fallback-цепочкой для каждого SEO-поля:
  1. Ручная правка через metabox (`_custom_seo_*`) — высший приоритет
  2. Все известные ключи популярных SEO-плагинов (`_yoast_wpseo_*`, `rank_math_*`, `_aioseo_*`, `_seopress_*`, `_su_meta_*`, `_genesis_*`)
  3. Гарантированный fsr fallback (`fsr_title`, `fsr_description`, `fsr_headline`)
  4. Стандартные WP-поля (`post_title`, `post_excerpt`) или авто-excerpt из контента
* **Фикс 3: новый metabox «Site Builder SEO».** Плагин добавляет панель в редактор поста/страницы с 6 полями:
  * **SEO Title** — заголовок вкладки браузера (пишется в `_custom_seo_title`)
  * **Meta Description** — описание для поисковиков (`_custom_seo_desc`)
  * **Social Headline** — заголовок для Open Graph и Twitter Cards (`_custom_seo_headline`)
  * **OG Description** — отдельное описание для соцсетей (`_custom_seo_og_desc`)
  * **Custom OG Image URL** — переопределение картинки для расшаривания (`_custom_seo_og_image`)
  * **noindex** — чекбокс скрытия страницы от поисковых систем (`_custom_seo_noindex`)
* **Умные плейсхолдеры**: каждое поле в metabox показывает **что будет использовано если оставить пусто** — берётся из fallback-цепочки. Разработчик сразу видит текущее автоматическое значение и решает — переопределить или оставить.
* **noindex-логика**: при активной галочке страница получает `<meta name="robots" content="noindex,nofollow">` в head, JSON-LD schema разметка **не выводится** (не имеет смысла для скрытых страниц).
* **Metabox условный**: показывается только когда сторонние SEO-плагины (Yoast, RankMath, AIOSEO, SEOPress, TSF) не установлены. Если Yoast активен — его собственный богатый metabox лучше, наш скрывается чтобы не путать.
* **Совместимость с существующими данными**: если разработчики уже правили `_custom_seo_*` через ACF или другие плагины — эти значения продолжат работать как раньше, metabox их подхватит и покажет для редактирования.

= 1.1.3-beta4 =
* **Умная перелинковка внутренних ссылок.** Реализация решает проблему кросс-ссылок между статьями, когда часть страниц публикуется по расписанию `[DLY]`. Раньше ссылка на страницу, которая ещё не опубликована, вела на 404 — теперь она автоматически становится обычным текстом до момента публикации целевой страницы. После публикации (в том числе автоматической — когда наступит запланированная дата) ссылка появляется сама, без ручных действий.
* **Как работает.** Решение состоит из двух частей — по одной с каждой стороны:
  * **При импорте** (плагин): каждая **относительная** ссылка `<a href="/some-path/slug/">Текст</a>` в контенте страницы конвертируется во встроенный шорткод `$$LINK slug | Текст$$`. Slug извлекается из последнего сегмента пути, расширение `.html` при наличии обрезается. **Внешние ссылки** (http/https/mailto/tel/якори) не трогаются — они рендерятся как есть, а модуль `external-links.php` при выводе добавит `target="_blank" rel="nofollow noopener"`.
  * **При рендере** (тема, модуль `inc/link-resolver.php`): фильтр `the_content` находит `$$LINK slug | текст$$` и проверяет slug в кэше опубликованных страниц. Если страница опубликована — рендерит нормальную `<a href="...">текст</a>`. Если нет — только «текст» без ссылки.
* **Автоматическая инвалидация кэша.** Модуль слушает WordPress-хуки `save_post`, `deleted_post`, `trashed_post`, `untrashed_post` и **`future_to_publish`** (последний срабатывает когда запланированный пост наступает по времени и становится опубликованным). При любом из этих событий кэш сбрасывается, и на следующем показе страниц соответствующие `$$LINK$$` автоматически превращаются в реальные ссылки. Ничего не нужно перепубликовывать вручную.
* **Совместимость с оригинальным решением коллеги.** Использованный синтаксис `$$LINK slug | text$$` полностью совпадает с тем, что использует ваша Python-пайплайн-команда — сайты которые уже содержат этот шорткод продолжат работать без изменений после подключения нашей темы.
* **Производительность.** Кэш slug→permalink живёт в WordPress-транзиенте (24 часа), плюс мемоизация внутри запроса — так что даже страница с сотней внутренних ссылок делает **один** DB-запрос за карту slug'ов.

= 1.1.3-beta3 =
* **Фикс: `[sb_year]` и `[sb_date]` теперь рендерятся в заголовках страниц, меню, хлебных крошках и админке.** WordPress автоматически применяет обработку shortcodes **только** к содержимому статьи (`the_content`), но не к заголовкам, меню, `<title>` вкладки браузера и другим местам где текст выводится как есть. В результате `[sb_year]` там оставался как литеральный текст.
* **Решение**: модуль `inc/shortcodes.php` в теме теперь подключает фильтры на всех соответствующих WordPress-хуках (`the_title`, `nav_menu_item_title`, `document_title_parts`, `wp_title`, `the_excerpt`, `get_the_excerpt`, `widget_title`) — как только в тексте встречается `[sb_`, он проходит через обработку. Обычные заголовки без наших shortcodes не трогаются (проверка на префикс `[sb_` работает как быстрый выход).
* **Также в SEO-модуле** (`inc/seo.php`): значения из мета-полей `_custom_seo_title`, `_custom_seo_desc`, `_custom_seo_headline`, `fsr_headline` тоже теперь проходят обработку — они читаются напрямую из БД, минуя стандартные фильтры WordPress.
* **Работает и на старых постах** без переимпорта: фильтры применяются при **выводе**, а не изменяют данные в БД. Как только тема пересобрана — все ранее импортированные страницы автоматически показывают год вместо `[sb_year]` во всех местах.

= 1.1.3-beta2 =
* **Дата в контенте теперь локализуется динамически.** Раньше плейсхолдер `$$CURRENT_DATE$$` в исходных `.md` заменялся на текстовую дату при импорте — в результате получалась дата на языке WordPress-админки (обычно русский), даже когда сам контент испанский или итальянский. Теперь плейсхолдер конвертируется в **shortcode** `[sb_date]`, который тема отрендерит на лету с использованием актуальной локали сайта в момент показа страницы:
  * `[sb_date]` — выводит дату последнего изменения статьи (`post_modified`). Если статью правили — покажет свежую дату
  * `[sb_date basis="published"]` — если нужна именно дата публикации (не редактирования)
  * `[sb_date format="j F Y"]` — можно задать формат по правилам PHP `date()`
  * `[sb_year]` — просто текущий год (для `$$CY$$`)
* **Внимание для существующих сайтов**: постов с уже вставленной русской датой это изменение не тронет — они как были с текстом «24 июня 2026», так и останутся. Чтобы обновилось, надо перезапустить FSR-импорт (плагин заменит на shortcode при новом парсинге). На новых импортах всё сразу правильно.
* **Валидация HTML на подвале — фикс.** Заголовки колонок футера («Навигация», «Сайт») выводились как `<h4>` — валидатор ругался, что после `<h2>` статьи идёт `<h4>` пропуская уровень. Изменено на `<h2>` (заголовки семантически равноценны заголовку статьи, оба на уровне «раздел»). CSS не менялся — стили заголовков в футере одинаковые независимо от тега.
* **Рандомизация времени публикации DLY-страниц.** Раньше все запланированные `[DLY]` статьи публиковались ровно в 00:00 — очевидный признак робота-планировщика. Теперь каждой странице назначается время в промежутке **9:00–22:00 локального времени**, детерминированно (при повторном импорте той же папки — то же время). Это применяется:
  * К `[DLY]` без даты в режимах `one_day` и `period`
  * К `[DLY=YYYY-MM-DD]` с явной датой — время суток тоже рандомизируется в рамках указанного дня
  * Не применяется к режиму `instant` (там DLY-страницы публикуются немедленно и время не имеет значения)

  2. **PHP fallback** — `the_post() → the_title() → the_content()`, выполнялся всегда, даже после инжекции
  
  После инжекции главная выводила содержимое **дважды**: один раз без h1 (инжектированный блок), один раз с h1 + the_content (fallback). Визуально пользователь видел длинный дублированный контент, в котором первый блок начинался с изображения, а где-то посередине терялся h1.
* **Фикс.** Убрал маркер из `base/front-page.php` сгенерированной темы. Логика `Site_Builder_FSR_Importer::inject_into_theme_front_page()` сама детектирует: «маркера нет + `the_content()` есть → не модифицировать файл». В результате на главной работает стандартный WordPress-цикл: `the_title('<h1>', '</h1>')` + `the_content()`. Один раз, без дублирования, с h1 в начале.
* **Совместимость со старыми темами не нарушена.** Механизм инжекции через маркер остаётся для тем, которым он нужен (legacy minipages с захардкоженным HTML вокруг маркера) — там логика срабатывает как раньше.
* **Тонкий момент:** в docblock-комментарии front-page.php первоначально упоминался текст маркера `"<!-- Enter Code -->"` как описание прошлого поведения. Эта строка тоже попала бы под `strpos()` в инжекции и сломала бы PHP-синтаксис. Переформулировал комментарий чтобы строка маркера в файле не встречалась нигде, даже в комментариях.

= 1.1.2-beta2 =
* **Фикс: пропадание h1 на главной странице (и в любой странице без YAML frontmatter).**
* **Корень проблемы.** В `parse_md_file()` и `parse_html_file()` плагин намеренно вырезает первый h1 из body — комментарий гласил «h1 redundant with the page title» (логика родом из minipages-темы, где h1 выводился отдельно через `the_title`). Но если у архива нет YAML frontmatter с явным `title:`, то `title` остаётся пустой строкой, а первый h1 уходит в небытие. Для root-страницы это критично — у неё ещё и `slug` пустой, поэтому `post_title = ''`, и `the_title('<h1>', '</h1>')` выводит пустой `<h1></h1>`. На главной h1 исчезает.
* **Фикс.** В обеих функциях парсинга, *перед* вырезанием первого h1, проверяем: если `title` пуст — используем h1 как title-fallback. Frontmatter `title:` (либо HTML `<title>`) сохраняет приоритет, фикс срабатывает только когда title пустой. Inline-плейсхолдеры (`$$CY$$`, `$$SITE_NAME$$` и т.п.) корректно применяются к title через уже-существующий `replace_inline_shortcodes()`.
* **Где применяется.** Все страницы FSR-импорта получают непустой `post_title`. На главной h1 рендерится через `the_title`. На обычных страницах через `page.php`. В sitemap, breadcrumbs, заголовке вкладки браузера, og:title — везде теперь корректный заголовок вместо slug-ish.

Используется `get_stylesheet_directory()` (поддержка child-тем) с `filemtime()` для cache-busting.
* **Предупреждение при нестандартном `front-page.php` темы.** Если у активной темы есть `front-page.php`, в котором **нет** ни `the_content()`, ни нашего маркера `<!-- Enter Code -->`, главная страница может отображаться пустой. Раньше плагин в этом случае молча дописывал HTML в конец файла темы (что часто ломало вёрстку). Теперь плагин в такой ситуации **не модифицирует файл темы** и записывает в журнал импорта warning с инструкциями: добавить маркер в шаблон темы, сменить тему, или принять пустую главную. Если в шаблоне есть `the_content()` (обычные темы), `do_blocks()` (block-темы) или наш маркер — поведение прежнее (стандартный путь WP либо инжекция).
* **Debug-сообщения `fsr_menu_debug` удалены** — они помогли диагностировать проблему с Main Auto Menu в beta9–10 и больше не нужны. Журнал импорта снова чистый: остаются только реальные warning'и и ошибки.

* **Фикс: картинки на страницах получали битый URL `http://IMAGES/foo.webp`.** Внутри `md_to_html()` я вызывал `esc_url()` для src картинок до того, как image-resolver успевал их разрезолвить. WordPress `esc_url()` для **относительных** путей (типа `IMAGES/foo.webp` или `../../IMAGES/foo.webp`) автоматически добавляет схему `http://`, превращая первый сегмент в имя хоста. Относительные пути сохраняются как есть и доходят до резолвера в исходном виде.

* Исправлен баг иерархии страниц: если в hub/images лежала картинка с именем, совпадающим со слагом страницы (например `kryptomeny.webp` для страницы `kryptomeny`), WordPress переименовывал страницу в `kryptomeny-2`, что ломало вложенность дочерних страниц и хлебные крошки. Теперь страницы получают свой слаг приоритетно перед attachment-конфликтом.
* UI: поле «Вложенных страниц сразу» автоматически скрывается в режиме «Опубликовать всё сразу», где оно не применяется.
