Внутренний инструмент массового импорта контента в WordPress.

== Description ==

Site Builder — это плагин для автоматического развертывания WordPress-сайтов из подготовленных архивов контента. Поддерживает два режима:

* **Создание сайта** — полный импорт сайта с нуля, включая главную страницу, подвал, стили и структуру вложенных страниц.
* **Добавление страниц** — расширение уже работающего сайта дополнительными статьями.

В обоих режимах поддерживается отложенная публикация: можно опубликовать всё сразу, по странице в день, либо растянуть публикации на заданный период.

Любой импорт можно полностью откатить — плагин хранит точку отката последнего запуска.

== Installation ==

1. В админке WordPress откройте «Плагины → Добавить новый → Загрузить плагин».
2. Выберите ZIP-файл плагина и нажмите «Установить сейчас».
3. После установки нажмите «Активировать».
4. В сайдбаре админки появится пункт меню «Site Builder».

== Changelog ==

= 1.0.0-beta11 =
* **Этап Е — отвязка от конкретной темы.** Плагин теперь работает на любой теме, а не только на нашей `minipages`.
* **Автоматическая привязка меню к локациям темы.** В Настройки добавлены два dropdown: «Привязать Main Auto Menu к локации:» и «Привязать Footer Auto Menu к локации:». Список локаций строится через стандартный WP-API `get_registered_nav_menus()` — это всё, что объявила активная тема. При FSR-импорте плагин делает `set_theme_mod('nav_menu_locations', […])` с выбранными привязками. Раньше пользователю нужно было вручную идти в *Внешний вид → Меню → Управление расположением* и привязывать каждое меню — теперь это происходит автоматически.
* **Опция «Не привязывать»** оставлена дефолтом — пользователи, которые предпочитают ручную привязку, ничего не замечают.
* **Защита от «протухших» локаций.** Если в Настройках сохранена локация, которой нет в текущей теме (например, тема сменилась), в dropdown появляется маркер «(нет в текущей теме)» и красное предупреждение. При импорте такая локация просто игнорируется и в журнал пишется warning.
* **Прежняя привязка локации снапшотится для отката.** При откате FSR-импорта `nav_menu_locations` восстанавливается в предыдущее состояние через уже существующий механизм `theme_mod:` префикса. Если до плагина в локации было меню — оно вернётся; если не было — локация снова станет пустой.
* **Block-темы (FSE).** Если активная тема не объявляет ни одной локации (Twenty Twenty-Four/Five и подобные block-темы используют блоки навигации вместо локаций), карточка в Настройках показывает предупреждение, а dropdown'ы не отображаются. Меню всё равно создаются и пункты в них добавляются — встроить их на сайт нужно вручную через редактор сайта.
* **styles.css теперь подключается из плагина независимо от темы.** Раньше плагин копировал стили в `theme/imported-styles/style.css`, но тема должна была сама подключить их через `wp_enqueue_style` — наша `minipages` это умела, чужие темы — нет. Теперь хук `wp_enqueue_scripts` живёт в плагине (`class-frontend.php`) и подключает файл автоматически. Путь хранения (в папке темы) остался прежним — для миграции с прежних beta-версий без перетаскивания файлов. Используется `get_stylesheet_directory()` (поддержка child-тем) с `filemtime()` для cache-busting.
* **Предупреждение при нестандартном `front-page.php` темы.** Если у активной темы есть `front-page.php`, в котором **нет** ни `the_content()`, ни нашего маркера `<!-- Enter Code -->`, главная страница может отображаться пустой. Раньше плагин в этом случае молча дописывал HTML в конец файла темы (что часто ломало вёрстку). Теперь плагин в такой ситуации **не модифицирует файл темы** и записывает в журнал импорта warning с инструкциями: добавить маркер в шаблон темы, сменить тему, или принять пустую главную. Если в шаблоне есть `the_content()` (обычные темы), `do_blocks()` (block-темы) или наш маркер — поведение прежнее (стандартный путь WP либо инжекция).
* **Debug-сообщения `fsr_menu_debug` удалены** — они помогли диагностировать проблему с Main Auto Menu в beta9–10 и больше не нужны. Журнал импорта снова чистый: остаются только реальные warning'и и ошибки.

= 1.0.0-beta10 =
* **Найдена и исправлена реальная причина исчезновения `Main Auto Menu`.** Из debug-логов beta9 стало видно: меню **создавалось** успешно (`term_id=51`), а потом *исчезало* — но Footer Auto Menu (term_id=52) оставался. Это указало на разницу в обработке: что-то знало про имя `Main Auto Menu` и удаляло именно его.
* **Виновник:** legacy-код в `Site_Builder_Wipe_Handler::finalize_wipe()`. В CREATE-режиме меню создаётся **после** wipe-фазы — и `finalize_wipe()` оправданно вычищает старые легаси-меню перед этим. В FSR логика обратная: меню создаются в `fsr_start` (раньше wipe-задач в очереди), а потом `wipe_finalize` срабатывала и удаляла свежесозданное `Main Auto Menu` (Footer не страдало, т.к. в `finalize_wipe` захардкожено имя только Main).
* **Фикс:** `finalize_wipe()` теперь принимает параметр `$preserve_menus`. Для FSR-импортов передаём `true` — меню остаются нетронутыми. Для legacy CREATE поведение не изменилось.
* Debug-сообщения с пометкой `fsr_menu_debug` оставлены в этой версии — они помогли диагностировать баг. В следующей версии (после твоего подтверждения работы) уберу их, чтобы не засорять журнал.

= 1.0.0-beta9 =
* **Диагностика проблемы с `Main Auto Menu`.** В beta8 я думал, что проблема — в кеше после `wp_delete_nav_menu`/`wp_create_nav_menu`, но фикс не помог. Значит причина другая: возможно остался orphaned term в БД от старых импортов (запись в `wp_terms` без соответствующей `wp_term_taxonomy` для `nav_menu`), либо плагин на сайте перехватывает хук `wp_update_nav_menu` и блокирует создание.
* **Многоуровневый fallback с подробным логированием.** Теперь каждый шаг подготовки меню пишет в журнал импорта (раздел «Ошибки и предупреждения» во вкладке Отчёт) что он попытался сделать и какой получил результат. Стратегия:
  1. `wp_get_nav_menu_object($name)` — если найдено и режим ADD, переиспользуем
  2. Если найдено в CREATE — `wp_delete_nav_menu` с принудительным сбросом term cache
  3. `wp_create_nav_menu` (стандартный путь)
  4. Если упал — повторный поиск через `wp_get_nav_menu_object`
  5. Поиск через `get_term_by('slug', ...)` — для случаев когда меню есть под другим именем
  6. Последний шанс — прямой `wp_insert_term` (обходит логику wp_create_nav_menu)
  7. Если `wp_insert_term` вернул `term_exists` — пытаемся получить term по указанному id
* **Что делать пользователю:** после установки beta9 и запуска FSR-импорта откройте вкладку **Отчёт** → раздел «Ошибки и предупреждения». Там будут debug-сообщения с пометкой `fsr_menu_debug` — пожалуйста, скопируйте их и пришлите. По логам станет ясно, на каком именно шаге процесс ломается, и я сделаю точечный фикс.

= 1.0.0-beta8 =
* **Фикс: `Main Auto Menu` не создавалось.** Имя «Main Auto Menu» использовалось ещё в legacy CREATE-режиме, и на многих сайтах меню с этим именем уже существовало от прошлых импортов. В FSR я делал `wp_delete_nav_menu()` + `wp_create_nav_menu()`, но у WordPress есть известная проблема: между этими двумя вызовами term cache может не успеть обновиться, и `wp_create_nav_menu()` возвращает `WP_Error('menu_exists')` — даже после успешного удаления. В результате `menu_main_id` становился `0`, и пункты с флагом `[M]` пропускались. Footer Auto Menu не страдало этим багом — имя новое (с beta1), на сайтах его раньше не было, поэтому delete не вызывался и проблема не проявлялась.
* **Решение:** добавлен helper `ensure_menu_ready()` с устойчивой стратегией:
  * Принудительный сброс term cache после `wp_delete_nav_menu()` через `clean_term_cache()` + `wp_cache_delete('last_changed', 'terms')`.
  * Если `wp_delete_nav_menu()` вернул false — не создаём новое, а **очищаем пункты существующего меню и переиспользуем его term_id**.
  * Если `wp_create_nav_menu()` всё равно упал с ошибкой — делаем повторный `wp_get_nav_menu_object()` и переиспользуем найденное меню.
  * Если совсем ничего не получилось — пишем warning в журнал импорта, импорт продолжается (страницы создаются, флаги `[M]/[F]` просто не применяются).

= 1.0.0-beta7 =
* **Фикс: кнопка «Создать сайт» не работала.** В beta6 я перенёс рендер всех кнопок шага «Запуск импорта» в динамический JS (renderActionBlock), включая скрытую «бридж»-кнопку `#sb-fsr-start-btn`, на которую wireImporter навешивает обработчик клика. Но jQuery `.on('click', '#id')` биндится только к элементам, которые уже есть в DOM на момент вызова. Поскольку wireImporter выполняется при загрузке страницы (когда динамический рендер ещё не сработал), кнопка `#sb-fsr-start-btn` отсутствовала, обработчик не вешался — и реальные кнопки «Создать сайт» / «Добавить страницы» (которые программно триггерили клик по `#sb-fsr-start-btn`) ничего не делали. Вернул `#sb-fsr-start-btn` и `#sb-fsr-cancel-btn` в статичный HTML (`tab-fsr.php`) — теперь wireImporter находит их при инициализации, как и должно быть. Визуальные кнопки и режим (create/add) по-прежнему рендерятся динамически, это работает корректно.

= 1.0.0-beta6 =
* **Этап Д — защита и режим расширения (FSR ADD).**
* **Защита от случайной перезаписи.** Если на сайте уже есть страницы, шаг «Запуск импорта» теперь не позволяет запустить полное создание сайта без явного подтверждения. Вкладка автоматически переключается в режим «развилки» с двумя кнопками:
  * **«Создать сайт заново»** — полная переустановка: удаление существующих страниц, пересоздание меню, замена лого/иконки/стилей. Требует ввода `УДАЛИТЬ` для подтверждения (та же логика, что в legacy CREATE-режиме).
  * **«Добавить страницы»** — режим расширения, безопасный для существующих данных.
  * На пустом сайте — одна кнопка «Создать сайт», как и раньше.
* **Новый режим FSR ADD.** Расширение существующего сайта новым FSR-архивом:
  * Существующие страницы с тем же slug+parent **пропускаются** (с сообщением «Уже существует», не как ошибка)
  * Корневая страница архива (`index.md`) НЕ заменяет главную сайта (`page_on_front` не трогается, инжекция в `front-page.php` темы пропускается)
  * Меню `Main Auto Menu` и `Footer Auto Menu` **переиспользуются** если уже есть (новые пункты `[M]`/`[F]` просто добавляются к существующим). Если меню нет — создаются. **Не удаляются и не пересоздаются.**
  * `logo.png`, `icon.png`, `styles.css` **не обрабатываются** (init_site_assets пропускается)
  * Все остальные функции работают как обычно: маппинг полей, картинки в страницах, флаги `[U]/[A]/[W]/[N]/[E]`, расписание `[DLY]`
* **Откат корректен в обоих режимах.** В ADD-режиме откат удаляет только то, что плагин добавил: новые страницы, новые пункты меню, новые картинки в медиатеке. Существующие данные (включая меню, у которого добавились новые пункты) остаются нетронутыми.

= 1.0.0-beta5 (deprecated) =
* **Этап Г — расписание DLY и видимость legacy-режимов.**
* **Расписание для `[DLY]`-страниц.** На втором шаге FSR-импорта (после маппинга) появился выбор расписания:
  * «Публиковать всё сразу» — `[DLY]` игнорируется, все страницы публикуются мгновенно

* Логика: страницы с `[DLY]` без даты получают будущую дату по расписанию (`post_status = 'future'`, WP-cron автоматически переведёт в `publish` когда наступит). Страницы с `[DLY=YYYY-MM-DD]` публикуются на указанную дату. Страницы без `[DLY]` публикуются мгновенно.
* Sequence index (`dly_seq`) присваивается каждой DLY-странице в `Task_Builder` при сборке очереди — это делает даты **детерминированными** независимо от того, в какой батч страница попадёт при обработке.
* **Видимость legacy-режимов.** В «Настройки» добавлен раздел «Видимость legacy-режимов» с тремя чекбоксами:
  * Показывать вкладку «Создание сайта»
  * Показывать вкладку «Добавление страниц»
  * Показывать вкладку «MD Restore»
  * Все три **выключены по умолчанию**. Старые режимы остаются доступны для совместимости со старыми архивами и аварийного восстановления, но не загромождают основной UI. Включаются одним кликом в Настройках.
* **Фикс: версия плагина в правом нижнем углу.** В стандартный WordPress admin footer (правый нижний угол) на страницах плагина теперь подставляется текст `Site Builder v1.0.0-beta5` (раньше там показывалась устаревшая или WordPress-версия). На остальных страницах admin не вмешиваемся — WordPress показывает свою стандартную информацию.

= 1.0.0-beta4 =
* **Фикс: картинки на страницах получали битый URL `http://IMAGES/foo.webp`.** Внутри `md_to_html()` я вызывал `esc_url()` для src картинок до того, как image-resolver успевал их разрезолвить. WordPress `esc_url()` для **относительных** путей (типа `IMAGES/foo.webp` или `../../IMAGES/foo.webp`) автоматически добавляет схему `http://`, превращая первый сегмент в имя хоста. В итоге к моменту работы резолвера src уже был полноценным абсолютным URL, и резолвер пропускал картинку по своему правилу «абсолютные URL не трогаем». Заменил `esc_url()` на `esc_attr()` для img src в двух местах (figure-блок и одиночные картинки) — это правильный эскейп для HTML-атрибута, не добавляет схему. Относительные пути сохраняются как есть и доходят до резолвера в исходном виде.

= 1.0.0-beta3 =
* **Этап В — картинки, лого/иконка, стили.**
* **Загрузка картинок из IMAGES/.** Каждая ссылка `<img src="...">` в HTML страницы (из `![alt](src)` в md или `<img>` в html) теперь резолвится в реальный файл и загружается в медиатеку WP. Стратегия поиска: 1) относительный путь от md, 2) `IMAGES/<basename>`, 3) папка самой страницы, 4) рекурсивный поиск по всему архиву по имени файла. Если файл не нашёлся — `src` остаётся как есть, в отчёт записывается warning «Не найдена картинка». Дедупликация по содержимому файла (md5_file) — одна и та же картинка не загружается дважды, даже если есть несколько физических файлов-копий.
* **Featured Image из headimg.** Поле `headimg` из frontmatter теперь загружается как Featured Image страницы через стандартный `set_post_thumbnail()`. Тема может использовать его через `get_the_post_thumbnail_url()` или `has_post_thumbnail()`.
* **Шестой слот маппинга «Featured Image / og:image».** На экране маппинга появилась шестая строка. URL загруженной картинки записывается в выбранные мета-поля (по умолчанию `_yoast_wpseo_opengraph-image` и `rank_math_facebook_image`). Можно выбрать другие или добавить свой через input «Свой meta_key».
* **logo.{png,jpg,svg,ico}** в `IMAGES/` корня архива загружается в медиатеку и устанавливается как `custom_logo` темы (`set_theme_mod`) и `site_logo` опция. Большинство современных тем читают одно из этих значений.
* **icon.{png,jpg,svg,ico}** в `IMAGES/` корня загружается и устанавливается как `site_icon` (favicon WordPress).
* **styles.css** в корне архива копируется в `wp-content/themes/<active>/imported-styles/style.css`. Папка `imported-styles/` создаётся если её нет. Тема может подключить эти стили через `wp_enqueue_style` из своего `functions.php`.
* **Расширение отката.** `rollback_option` распознаёт префикс `theme_mod:` и восстанавливает theme_mod (а не option). `rollback_theme_file` корректно различает «файл существовал, восстановить контент» и «файл не существовал, удалить созданный нами» (по флагу `original = null`). Откат FSR-импорта теперь корректно убирает лого, иконку и стили вместе со страницами.
* **Новый тип задачи `fsr_init`.** Init-операции (лого/иконка/стили) выделены в отдельную первую задачу очереди (depth=-1, выполняется до всех страниц). Это даёт прогресс-бар в UI и единое место для логирования.

= 1.0.0-beta2 =
* **Диагностика флагов.** Block Editor в WordPress не отображает сериализованные массивы в стандартной панели Custom Fields — `fsr_flags` всегда хранится как массив, поэтому в UI выглядит пустым (хотя данные в БД есть). Чтобы можно было быстро убедиться, что флаги распарсились правильно, добавлены два механизма:

* Карточка «Активный импорт» в шапке страницы плагина показывает данные текущего активного импорта, прогресс и кнопку «Прервать и сбросить». Это позволяет вручную разблокировать застрявший импорт (вместо ожидания 5 минут до автоматического протухания heartbeat).
* Если на сервере есть запись об активном импорте — обе формы запуска (CREATE и ADD) блокируются на UI до сброса блокировки.
* Подсказка пользователю: если последний heartbeat был более 30 секунд назад, карточка активного импорта подсвечивается жёлтым и сообщает, что импорт, скорее всего, прерван и его можно сбросить.

Кнопка по умолчанию `disabled` в HTML, но JS не активировал её в случае, когда подтверждение «УДАЛИТЬ» не требовалось. Проблема проявлялась после полной очистки сайта (например, через WP Reset).

= 0.2.3 =
* Новый чекбокс «Ждать 1 неделю перед публикацией отложенных страниц» на вкладке «Создание сайта». Если включён, все отложенные публикации (то, что выходит не мгновенно) сдвигаются на 7 дней вперёд. Полезно для SEO-«прогрева» сайта первыми страницами. Чекбокс не показывается в режиме «Опубликовать всё сразу».

= 0.2.2 =
* Исправлен критический баг с миниатюрами страниц: при дедупликации картинок плагин ориентировался на имя файла, а не на его содержимое. В типичных архивах каждая страница имеет свой `hero.webp`, но плагин загружал только первый встретившийся и подставлял его как миниатюру всем последующим страницам. Теперь дедупликация идёт по md5-хэшу содержимого: реально одинаковые картинки переиспользуются, разные — загружаются отдельно (WordPress сам делает имена файлов уникальными).
* Главная страница теперь получает миниатюру из первой картинки HUB-индекса — раньше она оставалась без миниатюры.

= 0.2.1 =
* Исправлен баг иерархии страниц: если в hub/images лежала картинка с именем, совпадающим со слагом страницы (например `kryptomeny.webp` для страницы `kryptomeny`), WordPress переименовывал страницу в `kryptomeny-2`, что ломало вложенность дочерних страниц и хлебные крошки. Теперь страницы получают свой слаг приоритетно перед attachment-конфликтом.
* UI: поле «Вложенных страниц сразу» автоматически скрывается в режиме «Опубликовать всё сразу», где оно не применяется.
